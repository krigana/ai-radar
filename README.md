# AI-радар — нові AI-сайти та на чому їх роблять

Каталог свіжих AI-стартапів на даних публічного API [FreeSerp](https://freeserp.ai/docs.php) (`index=sites`, ніша AI): пошук, фільтри за нішею, стеком, датою запуску й Domain Rating, сортування та порівняння до трьох сайтів поруч.

Тестове завдання на вакансію **Junior AI Web Developer**.

- **Демо:** https://web-service.studio/ai-radar — розділ на сайті моєї веб-студії, у її дизайні.
- **План сайту** (мета, аудиторія, сторінки, структура): https://web-service.studio/ai-radar/plan, а також [PLAN.md](PLAN.md).

## Що зроблено

- **Пошук** за ключовими словами (`q`) по індексу AI-сайтів.
- **Фільтри:** ніша (44 підніші FreeSerp з українськими назвами), стек сайту (Next.js, Lovable, v0, Bolt, Base44, WordPress, Shopify, «ймовірно згенерований AI»), період запуску (7 / 30 / 90 / 365 днів), мінімальний Domain Rating.
- **Сортування:** спершу нові, спершу авторитетні (DR), за релевантністю (лише коли є пошуковий запит).
- **Картки сайтів:** домен, заголовок, AI-опис з FreeSerp (згорнутий, розгортається), ніші (клік по ніші фільтрує каталог), стек, DR, дата запуску.
- **«Показати ще»** — пагінація по 24 сайти.
- **Порівняння** до 3 сайтів у таблиці: найвищий DR і найсвіжіший запуск підсвічуються.
- **Стан фільтрів у URL:** посиланням на добірку можна поділитися, наприклад `/ai-radar?stack=lovable&sort=dr`.
- **Адаптивність:** на телефоні фільтри стають компактними, а швидкі ніші — горизонтальною стрічкою.

## Як запустити локально

Потрібен PHP 8.1+ з cURL (або дозволеним `allow_url_fopen`). Залежностей немає, збірка не потрібна.

```bash
git clone https://github.com/krigana/ai-radar.git
cd ai-radar
php -S localhost:8000 -t public public/index.php
```

Відкрийте http://localhost:8000. Сторінка ходить до FreeSerp через вбудований PHP-проксі `/api`.

**Тести на мок-даних** (без інтернету):

```bash
php -S 127.0.0.1:9001 tests/mock-freeserp.php                                         # мок FreeSerp
AI_RADAR_API_URL=http://127.0.0.1:9001/ php -S 127.0.0.1:8000 -t public public/index.php
npm i -D playwright && npx playwright install chromium && node tests/ui-check.js   # браузерні перевірки
```

`tests/ui-check.js` перевіряє завантаження, «Показати ще», фільтр за нішею, порівняння, відновлення фільтрів з URL, відсутність горизонтального скролу на телефоні й те, що HTML із даних API не виконується.

## Структура

```
public/index.php          автономна версія: сторінка + JSON-проксі /api
public/assets/ai-radar.js інтерфейс (чистий JS, без фреймворків)
public/assets/ai-radar.css стилі (префікс .air-, змінні з фолбеками)
src/AiRadar.php           ядро: перевірка параметрів, запит до FreeSerp, кеш
src/ai-radar-app.php      розмітка фільтрів, результатів і порівняння
tests/                    мок FreeSerp і браузерні перевірки
```

На web-service.studio ті самі `AiRadar.php`, `ai-radar-app.php`, JS і CSS підключені в PHP-сайт студії (маршрути `/ai-radar`, `/ai-radar/plan`, `/ai-radar/api`). Сам репозиторій сайту приватний, тому код модуля винесено сюди.

## Як це влаштовано і що виявилося по ходу

- **Серверний проксі замість запитів із браузера.** Документація FreeSerp каже, що CORS відкритий. На практиці API віддає заголовок `Access-Control-Allow-Origin: *, *` з подвоєним значенням, і браузери такі відповіді відхиляють: `fetch` зі сторінки падає з `Failed to fetch`. Тому сторінка звертається до власного `/api`, а PHP уже до FreeSerp. Заодно це дало:
  - **білий список параметрів:** у FreeSerp іде лише перевірене (ніша і стек тільки з відомих значень, DR у межах 0–100, ліміт пагінації API `from + size ≤ 10000`);
  - **кеш на 10 хвилин:** однакові запити не навантажують API;
  - **стійкість:** якщо FreeSerp тимчасово недоступний, віддається останній збережений результат, а для нового запиту показується зрозуміла помилка з кнопкою «Спробувати ще раз»;
  - **ідентифікацію:** запити підписані параметром `agent`, про що просить документація.
- **«За останні N днів» рахується від найсвіжішої дати в індексі, а не від сьогодні.** Індекс оновлюється із затримкою (найновіший `went_live` на момент роботи — 08.09.2026), тому фільтр «7 днів» від сьогоднішньої дати завжди повертав би порожній список.
- **Безпека виводу.** Усі дані з API вставляються в сторінку лише через `textContent`, без `innerHTML`; посилання на сторонні сайти відкриваються з `rel="noopener nofollow"`.
- **Сторінки закриті від індексації** (`noindex`): автоматично зібраний каталог без власного тексту не має потрапляти в пошук під доменом студії.

## Що не встиг

- Окремі сторінки ніші й сайту з людськими URL (`/ai-radar/nisha/...`, `/ai-radar/sajt/...`), які вже можна було б індексувати.
- Сторінку тенденцій: скільки AI-сайтів запускається щотижня в кожній ніші, яка частка конструкторів (Lovable, v0, Bolt).
- Обмеження частоти запитів до проксі за IP: зараз навантаження стримує лише кеш.

## Що доробив би далі

- Збережені добірки й підписку на нові сайти в ніші (email або Telegram).
- Фільтр-перемикач «прибрати великих гравців»: прапорець `ai_startups=1` у FreeSerp інколи пропускає великі давні сайти на кшталт bing.com або wiley.com.
- Переклад AI-описів українською на льоту (зараз описи англійською, як їх віддає FreeSerp).

## Як працював з AI

Робота велась у **Claude Desktop** (режим Cowork, модель Claude): з доступом до репозиторію сайту на моєму комп'ютері, вбудованим браузером і тестовим середовищем.

- **Рішення ухвалював я:** вбудувати проєкт у сайт студії, а не робити окрему демку; винести код модуля в окремий публічний репозиторій; ідею обрав з трьох запропонованих варіантів (AI-радар / підбір AI під задачу / конкуренти AI-стартапу).
- **Що робив Claude за моїми задачами:** дослідив реальні відповіді API (поля, значення ніш і стеків, ліміти), знайшов проблему з CORS і запропонував проксі, написав код, тестував на мок-сервері та в headless-браузері на десктопній і мобільній ширині, виправив знайдене (наприклад, на телефоні фільтри займали весь перший екран, тож швидкі ніші стали горизонтальною стрічкою).
- **Як перевірявся результат:** тести на мок-сервері FreeSerp (зламані параметри, недоступність API, кеш, XSS через дані API), браузерні перевірки й скриншоти на десктопній і мобільній ширині, фінальна перевірка розділу на живому сайті після деплою.
